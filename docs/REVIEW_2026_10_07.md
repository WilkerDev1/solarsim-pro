## Hallazgos y cambios

| Área | Fallo comprobado | Corrección y regresión |
| --- | --- | --- |
| Sesión | `validateSession` borraba el token ante fallos de red o 5xx. La prueba previa cubría otro camino de transporte. | Separar rechazo definitivo de indisponibilidad; conservar sesión ante errores transitorios. `testAuthTransportBoundaries.ts`. |
| Tokens | Colisiones reproducibles del hash FNV-1a de 32 bits podían confundir tokens distintos. | Claves SHA-256 por servidor/token, caché FIFO de 50 entradas y renovación compartida. Regresiones de colisión, login tardío y rechazo tras retry. |
| Borradores | Remontar Ajustes/centro por época de sesión borraba formularios sin guardar; renovar el token también reiniciaba formularios del equipo. | Separar identidad/ámbito del formulario y época de solicitudes; conservar borradores del mismo ámbito y descartar respuestas ajenas. Fixture `draftLifecycle` con transporte simulado. |
| Reautenticación | Recortar la contraseña impedía usar contraseñas válidas con espacios literales. | Enviar el valor exacto del campo de contraseña. |
| Historial web | Historial global y caché por ID de proyecto podían mostrar publicaciones de otra organización; una carga tardía podía contaminar el ámbito nuevo. | Separar por servidor/organización. Legacy sin pertenencia demostrable se conserva en cuarentena. `testSharedProposalScope.ts`, `testCloudflareShareHistory.ts`. |
| Modal de publicación | Respuestas tardías contaminaban aperturas posteriores; texto casi invisible en modo claro y URLs del servidor podían cambiar el origen. | Guardas por solicitud, ciclo y contexto; enlace HTTPS canónico desde el Worker seleccionado; contraste y nombres accesibles corregidos. `testShareModalRequestGuard.ts`. |
| Texto técnico | Sustituciones demasiado amplias podían reemplazar el nombre del cliente o el consumo resaltado por una descripción de paneles. | Sustituir solo el fragmento de módulos identificado, conservando texto personalizado y otros resaltados. `testSummaryText.ts` y `publicationIntegrity.test.ts`. |
| Compatibilidad | Un 401 anónimo se presentaba como acreditación de contratos autenticados que no se habían ejecutado. | Informar cobertura parcial, `WARN` y salida 1 por contratos no acreditados. `verifyDeploymentCompatibility.test.ts`. |
| Release | Los JSON tracked alterados no correspondían exactamente a los manifiestos remotos firmados. | Restaurar los manifiestos exactos y verificar la candidata con la clave GPG fijada. No reemplazar un documento firmado por una reconstrucción equivalente. |

Los revisores independientes inspeccionaron autenticación, aislamiento de datos, interfaz, publicación y releases. Los hallazgos se reproducen antes de cerrar; la revisión de código no sustituye el ensayo de runtime.

## Ensayo con runtime real

`server/tests/stagingEndToEnd.test.ts` sigue siendo una integración en proceso: PostgreSQL real, Hono en proceso, KV `Map` y fetch interceptado. No ejecuta workerd ni acredita QR. Se conserva por su cobertura rápida de contratos.

El nuevo runner `scripts/qa/runRuntimeStaging.ts` inicia PostgreSQL desechable, API con HTTP real, Wrangler local con workerd/KV privado y túneles HTTPS temporales. Los puertos se asignan dinámicamente; un nonce identifica los servicios QA antes de cada mutación de aprovisionamiento. Se eliminan variables de credenciales Cloudflare/DB heredadas, y la configuración rechaza destinos de producción. Al finalizar limpia procesos, contenedor, KV local, túneles y configuración de fixture de su propia ejecución.

Reproducción desde la raíz, con Node 24, Docker y dependencias instaladas:

```bash
QA_CLOUDFLARED=/ruta/al/binario/oficial/cloudflared npx tsx scripts/qa/runRuntimeStaging.ts
```

En otra terminal, `npm run dev`. Abrir `/scripts/qa/fixtures/runtimeFlow.html` sobre el origen local de Vite. La fixture monta `App` completa con servicios reales y almacenamiento QA separado. Usuarios sintéticos: Ana ADMIN, Bruno EDITOR, Vera VIEWER y Eva en otra organización, todos bajo `@staging.example.invalid`. Los tokens no se imprimen ni persisten en artefactos. `Ctrl+C` en el runner realiza la limpieza; no dejar túneles del ensayo activos.

Resultados observados:

- Ensayo HTTP real `stagingRehearsal.ts`: creación y CAS entre dos editores, rechazo VIEWER y cliente sin `baseVersion`, snapshots legacy/físico confirmados por política, papelera/restauración e inmutabilidad de una publicación existente en el KV local.
- Navegador con la aplicación completa: login Ana QA, equipo con tres roles, invitación de Eva QA, token sintético rechazado por la API real, aviso de reautenticación y recuperación de la sesión. Propuesta sintética sincronizada y publicación con enlace/QR visible.
- Ensayo separado `draftLifecycle`: borrador de membrete, perfil compartido con CAS y endpoint de integración preservados; ámbito B aislado. Aquí el transporte está simulado: acredita ciclo de vida de componentes y borradores, no la API.

El QR de la captura `runtime-share.jpg` se decodificó con jsQR y coincidió exactamente con el enlace HTTPS mostrado. La lectura pública respondió 200 y conservó el cliente sintético. Se guardó el perfil compartido por CAS y se creó una organización independiente C; el selector permitió cambiar A → C → A, recuperando el perfil de A. La repetición del ensayo HTTP real con las dependencias definitivas volvió a pasar; el runner cerró correctamente DB, KV local, túneles y configuración temporal. Las capturas y límites se registran en [QA del 7 de octubre](qa/review-2026-10-07/README.md). No se generaron ni modificaron propuestas empresariales para este ensayo.
