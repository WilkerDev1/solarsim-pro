# AGENTS.md

Guía canónica para agentes y desarrolladores. Producto y módulos: [README.md](README.md) y [docs/README.md](docs/README.md). Si un documento contradice el código, manda el código y se corrige el documento.

## Contratos vigentes

- **Modelo energético.** Legacy es el predeterminado: los motores (`src/engine/`) usan `legacy` si no reciben modo. La proyección física de autoconsumo/BESS es opcional: función `selfConsumptionProjection` en `shared/applicationFeatures.ts` con `defaultEnabled: false`, leída mediante el selector `useEnergyCalculationMode` (`src/features/application/`). Cambiar una etiqueta de UI nunca cambia el modelo de cálculo.
- **Funciones nuevas** se registran en `shared/applicationFeatures.ts` (default, etapa, visibilidad, disponibilidad) y se leen con el selector efectivo. Con sesión, la política de la organización (ADMIN mediante PATCH con `baseVersion`) prevalece sobre la preferencia local.
- **Agentes de IA**: toda capacidad para asistentes o agentes externos se declara en `shared/agentTools/definitions.ts` y se ejecuta con `executeAgentTool` (`src/features/agentTools/registry.ts`). Excepción: el conjunto del asistente de la app (F3a) declara sus herramientas propias en el cliente, `src/features/agentTools/appAssistant/definitions.ts`, y las ejecuta con `executeAssistantToolset` (que pasa por `runNativeTool`, con los mismos permisos), para no tocar las 12 herramientas remotas ni `AGENT_RULES_ES` (copias doradas); ver [el conjunto](docs/AGENT_TOOLS.md#conjunto-del-asistente-de-la-app-f3a). Tipos `read`/`draft`/`guarded`: `guarded` requiere confirmación humana salvo el modo bypass explícito (`guarded: 'allow'`; las herramientas sin deshacer siguen confirmándose) y salvo el perfil «edición en vivo» del asistente de la app (`agentPolicy.appAssistantProfile`, decidido solo en `src/features/agentTools/permissionProfile.ts`, [ADR 0010](docs/adr/0010-perfil-edicion-en-vivo.md)): lo que solo cambia una propuesta y tiene deshacer (precios, margen, extras y descuentos de `edit_proposal`) se aplica al momento con diff y deshacer; los agentes externos y lo compartido (catálogo, estado, papelera, borrados) siguen confirmándose; los kinds no cambian; las propuestas automáticas usan `AUTOMATED_PRICING`. Lo que ven los agentes externos (`AGENT_RULES_ES`, `REMOTE_INSTRUCTIONS`, las 12 herramientas remotas, la definición de `propose_project_update` y los kinds) está congelado hasta F7 y lo vigila `testFrozenAgentContract` con huellas que no regenera `UPDATE_GOLDEN` ([contrato congelado](docs/AGENT_CONTRACT_FREEZE.md)); las instrucciones del asistente de la app se componen en tres capas con `buildSystemInstruction` (la primera es `AGENT_RULES_ES` tal cual). El flotante corre en una sesión fuera de React y un bucle propio sobre `LlmClient` (`src/features/assistant/session/`, [ADR 0011](docs/adr/0011-sesion-y-bucle-del-asistente.md)): un turno entra en el historial solo cerrado (ningún `functionCall` sin su `functionResponse`, tampoco tras Stop), el contexto vivo va dentro de `functionResponse.response`, las declaraciones son fijas en el turno, el modelo de respaldo solo entra antes de la primera respuesta del modelo, sin reintentos del SDK ni continuación automática, y las llamadas se ejecutan en orden, una a una. Ver [docs/AGENT_TOOLS.md](docs/AGENT_TOOLS.md).
- **API** (`server/`): toda mutación usa CAS con `baseVersion` (409 en conflicto) y comprueba los permisos actuales en la base de datos, no solo los claims del JWT. Roles: ADMIN, EDITOR y LECTOR (`VIEWER` se acepta como alias y se normaliza a LECTOR). Migraciones numeradas en `server/src/database/` (la 006 quita el espejo de equipos de todos los proyectos; la 009 guarda logos y miniaturas de anexos una vez por organización en `document_assets` y las propuestas solo referencias `asset:sha256:`, que se sirven en línea a quien no pide `?assetRefs=1`; `shared/documentAssets.ts`; la 010 guarda los registros de precio de equipos en `equipment_price_observations`, fuera del catálogo y solo de inserción, [ADR 0006](docs/adr/0006-precio-generico-e-historial.md); la 011 crea `quotations` y `quotation_counters`: la API asigna el número `COT-AAAA-NNNN` al crear, por organización y año de emisión, en la misma transacción que la inserción, y nunca lo cambia ni lo reutiliza, [API](docs/DATABASE_AND_API_SPECIFICATION.md#cotizaciones-migración-011); la 012 crea `quotation_templates` y `quotation_signatures` (CAS, borrado lógico, `?since=`, una predeterminada), y `POST /api/document-assets` sube a `document_assets` un archivo suelto (PDF/PNG/JPEG/WebP verificado por su firma de bytes, 8 MiB) cuyo `asset:sha256:` usan logos, firmas, sellos y adjuntos de cotización, [API](docs/DATABASE_AND_API_SPECIFICATION.md#plantillas-y-firmas-de-cotización-migración-012)). Toda escritura de proyectos actualiza `updated_at` (el escritorio descarga solo lo cambiado) salvo migraciones que no cambian lo que lee un cliente. Las rutas de datos exigen `X-SolarSim-Client: <nombre>/<versión>` ≥ `MIN_CLIENT_VERSION` (426 `client_outdated`); un cliente nuevo debe enviarlo ([API](docs/DATABASE_AND_API_SPECIFICATION.md#versión-mínima-de-cliente)).
- **MCP remoto** ([docs/MCP_REMOTE.md](docs/MCP_REMOTE.md)): servicio aparte `mcp-remote/` (sin estado, sin credenciales de base ni `JWT_SECRET`) que reenvía tokens de agente `ssm_…` a la API. La API solo los acepta en `AGENT_ROUTES` (`shared/agentAccess.ts`), nunca en `/api/auth/*`; alcance `read` = LECTOR; las herramientas `guarded` no se exponen en remoto. Desactivado salvo `MCP_REMOTE_ENABLED=true`; OAuth 2.1 con `MCP_OAUTH_ENABLED=true`.
- **Registro público** crea siempre una organización nueva con su usuario ADMIN; nunca une a Electsun ni a otra organización existente. Las propuestas locales no se asignan automáticamente a una organización al iniciar sesión.
- **Clientes** ([docs/CLIENTS.md](docs/CLIENTS.md)): `clientId` en la propuesta es un enlace opcional, independiente de los datos impresos (`project.client`); enlazar o borrar un cliente nunca reescribe el documento. Validación en `shared/clients.ts`; escrituras con CAS y borrado lógico que desenlaza. Los clientes locales tampoco se asignan automáticamente a una organización.
- **Cotización desde propuesta** ([docs/QUOTATION_FROM_PROPOSAL.md](docs/QUOTATION_FROM_PROPOSAL.md)): el origen (`src/features/quotations/proposalSource.ts`) toma los importes solo de los resultados del motor (`contractPriceUSD`, descuento aplicado = lista − bruta, ITBIS no exonerado) y de `shared/financialRules.ts`, nunca de fórmulas de precio propias; total, ITBIS y base gravada cuadran al centavo con la propuesta también con descuentos: como en el motor, los descuentos se imputan a la parte sin ITBIS (la línea global, con una fila «Incluye descuento…» debajo), nunca como descuentos del documento que rebajarían lo gravado; lo que no cabe en esa línea va a los extras exentos visibles (cada uno con su fila), y solo el resto de un descuento mayor que todas las líneas sin ITBIS pasa al documento y deja una diferencia `totalDifferenceCents` (con signo) que el diálogo muestra y que nunca se compensa con una línea de ajuste (lo fija `testQuotationProposalSource`, con un fuzz de semilla fija). Convertir nunca modifica la propuesta; los documentos pasan solo como referencias reutilizables (`related`), sin copiar binarios.
- **Correo de cotizaciones** ([editor](docs/QUOTATION_EDITOR.md#correo)): la app no envía correos; asunto y cuerpo salen de `src/features/quotations/quotationEmail.ts` (puro), lo editado para un envío no se guarda en `QuotationContent`; los archivos «Aparte» y los anexos dentro del PDF salen de los destinos de cada adjunto (`shared/quotations/attachmentDestinations.ts`: `mode` `include`/`related` más `alsoSeparate`, que una API 2.10.1 descarta y el cliente conserva sin enviarlo nunca al salir de una bloqueada, [campos solo locales](docs/QUOTATIONS.md#campos-solo-locales); nunca valores nuevos en `mode`; el release redespliega la API antes del cliente), y el `mailto:` se arma solo con `buildMailtoUrl` (destinatario validado, sin saltos en asunto ni destinatario, tope `MAILTO_MAX_LENGTH`). Los enlaces externos del renderer se abren con `openExternalUrl` (`src/utils/openExternalUrl.ts`), nunca llamando al puente directamente: lista blanca estricta de `shared/externalUrl.ts` (http(s) con host; `mailto:` con una sola dirección válida y solo `subject`/`body`), que el IPC `open-external-url` vuelve a aplicar y responde con un booleano.
- **Pruebas**: ninguna escribe en producción. `scripts/testEnvironment.ts` hace fallar `fetch`; las suites inyectan transporte sintético. Las integraciones de API usan PostgreSQL efímero en Docker.
- **Imagen de la API**: `docker build -f server/Dockerfile .` desde la raíz del repositorio (necesita `shared/`), nunca desde `server/`.
- **Visor (Worker)**: los enlaces publicados conservan su `calculationSnapshot`; los enlaces antiguos sin metadatos deben seguir renderizándose.

## Invariantes

- `src/store/useSimulationStore.ts` solo compone `slices/` y persistencia; conservar todos sus exports públicos (p. ej. `NewProjectPayload`, `generateNextProjectSequence`, `findDuplicateProjectInfo`) y la API de cada slice.
- El renderer (`src/`) no importa módulos de Node; el acceso al sistema pasa por `electron/preload.ts` → `window.electronAPI`.
- `shared/` es TypeScript puro (excepción: `geminiTransport.ts`, fetch inyectable). `src/engine/` son funciones puras: no importan el store ni deciden permisos.
- Ley 57-07: crédito del 40% solo sobre equipos (paneles, inversores, baterías), aplicado en 3 cuotas anuales; inversión neta = precio de contrato − crédito. Medición neta según el régimen de la propuesta (`rates.netMeteringRegime`, `shared/netMetering.ts`, [ADR 0005](docs/adr/0005-regimen-medicion-neta-sie007.md)): el invariante de retención de exportación pertenece solo a `legacy_retention` (lo guardado sin el campo): la retención de exportación (25% por defecto) se aplica solo al excedente exportado; en `sie007_2026` (propuestas nuevas) se acredita todo lo inyectado y se descuenta un cargo en RD$/kWh inyectado solo en tarifas de un solo precio; con el precio de referencia y la fila de la tarifa guardada (`rates.energyRateSource`, `rates.billingTariff`) el ahorro es factura sin sistema − factura con sistema (`shared/tariffBilling.ts`, `resolveAssumptions(...).energyValuationMethod`). Antes de tocar fórmulas leer [docs/FINANCIAL_ENGINE_SPECIFICATION.md](docs/FINANCIAL_ENGINE_SPECIFICATION.md) y [docs/ENERGY_BALANCE_AND_SELF_CONSUMPTION_SPECIFICATION.md](docs/ENERGY_BALANCE_AND_SELF_CONSUMPTION_SPECIFICATION.md).
- Impuestos por ítem: `shared/financialRules.ts` es la única regla (`isItemItbisExonerated`, `appliesItemMargin`: margen activado salvo `applyMargin === false`, `customItemsTaxBreakdown`), usada por motor, interfaz y visor. Paneles e inversores nunca llevan ITBIS.
- Equipos: usar `shared/equipment` (`readEquipment`, `editEquipment`, `equipmentTotals`, `describeEquipment`, `migrateLegacySpecs`; `applyLegacyEquipmentPatch` solo traduce parches con campos sueltos) y nunca los campos sueltos del espejo (`panelBrandModel`, `panelCount`…), que `SystemSpecs` ya no declara: solo `LegacyProjectSpecs`/`LegacySystemSpecs` los tipan, y solo `shared/equipment`, la hidratación y la importación de `.json` pueden leerlos (los guarda `testNoEquipmentMirrorAccess` y `npm run lint`); ver [ADR 0001](docs/adr/0001-equipment-model-sin-espejo.md) y el [glosario](GLOSSARY.md). Motor, store, historial, importación y dock leen y escriben solo grupos; la aplicación ya no escribe el espejo. Al hidratar, importar y restaurar versiones se ejecuta `migrateLegacySpecs` (invariante, idempotente). DOD y eficiencia de batería son solo por grupo. `editEquipmentGroup`/`normalizeEquipmentEdit` (`src/utils/equipmentGroups.ts`) son compuertas de compatibilidad sobre el módulo para armar parches de `updateSpecs`. La energía útil y la autonomía del banco de baterías salen solo de `batteryBank`/`batteryAutonomyHours` (`shared/equipment/battery.ts`; [ADR 0002](docs/adr/0002-banco-de-baterias.md)); una prueba rechaza copias de la fórmula `capacidad × DOD × eficiencia`.
- Supuestos: los valores efectivos de cambio, pérdidas, inflación, descuento, vida del proyecto, cobertura, retención de exportación, vigencia, degradación, reemplazo de batería, $/W, margen y mano de obra salen solo de `resolveAssumptions` (`shared/assumptions.ts`, [ADR 0003](docs/adr/0003-supuestos-resueltos.md)); nadie escribe `|| 3.5` ni `?? 25` sobre esos campos (`testNoAssumptionDefaultLiterals`). Lo guardado al que le falta un dato usa la constante compartida, no los ajustes del usuario, que solo siembran propuestas nuevas.
- Edición de proyecto: toda edición de specs, tarifas, cliente, consumo, finanzas o precio de proveedor pasa por `applyProjectEdit` (`src/domain/projectEdit.ts`, puro; [ADR 0004](docs/adr/0004-edicion-de-proyecto.md)); las porciones del store solo persisten, sincronizan y deshacen. Un lote de ediciones por ruta del registro (`src/domain/projectFields.ts`) se aplica con `applyProjectEdits` (`src/domain/projectEditTransaction.ts`: todo o nada, independiente del orden, diff con derivadas y resultados del motor) y se escribe con `commitProjectEdits` (una escritura, un sello, un autosync y un paso de deshacer); el dock escribe así. Las reglas del dock (tarifa y perfil, margen %, precio directo, «Mejor proveedor», precio a mano, catálogo y lista de equipos) viven en `src/domain/rules/` y la transacción completa con ellas un lote por ruta (`src/domain/editIntents.ts`): el gesto del dock y su lote equivalente dejan el mismo proyecto (`testDockGesturesGolden`, `testDockRulesInDomain`). Mirar una propuesta nunca escribe: ningún `useEffect` del simulador llama a un escritor del proyecto (`testNoProjectEditRulesOutsideModule`); la reconciliación con el catálogo corre en la siguiente edición real; con el catálogo vacío (sin cargar, misma convención que los anexos) no se reconcilia ni se suelta ningún proveedor, tampoco al cambiar de modelo.
- Propuesta nueva: una sola fábrica pura, `createNewProposal` (`src/domain/newProposal.ts`, [ADR 0009](docs/adr/0009-fabrica-unica-dimensionado-y-propuesta-incompleta.md)), para «Nueva simulación», el asistente y los agentes: sin datos, 1.000 kWh/mes marcados como estimados; factor = «Margen bruto objetivo» de Ajustes (40 % de fábrica); 170 USD/kWp; la tarifa de referencia de la distribuidora a ese consumo; nada del caso de referencia; equipos del catálogo con el resolvedor de precios (nunca un precio inventado). El dimensionado vive en `src/domain/sizing.ts` con sus supuestos en `SIZING_ASSUMPTIONS`; `specs.sizingBasis` ausente (lo guardado) dimensiona con el consumo real, como siempre. Sin los mínimos para calcular, la propuesta es **incompleta** (`proposalCompleteness`, derivado): resultados vacíos con su motivo (nunca en cero) y sin PDF, compartir ni conversión a cotización.
- Equipos: `panels[]`/`inverters[]`/`batteries[]` son la fuente. Cada grupo recuerda su equipo del catálogo en `catalogItemId` (`selectCatalogEquipment`, `resolveGroupCatalogItem`); con él `ProposalAnnexSync` anexa solas las fichas PDF de los equipos en uso y la exportación consulta `proposalAttachmentResolver`; un grupo reescrito a mano (`manualModel`) o sin referencia al catálogo no cuenta como pendiente; con el catálogo sin cargar (vacío) y algún grupo en uso sin resolver se conservan todos los anexos automáticos, y con el catálogo cargado solo el de los ids a los que apuntan los grupos sin resolver (`catalogItemId`/`id`) ([docs/EQUIPMENT_CATALOG.md](docs/EQUIPMENT_CATALOG.md#fichas-anexadas-automáticamente)).
- Permisos: usar `shared/permissions.ts` (`canWrite`, `canAdminister`, `isWriterRole`…); una prueba falla ante comprobaciones de rol en línea. Las propuestas en papelera son de solo lectura en el store.
- PDF: seguir [.agents/rules/html2canvas_pdf_export_rules.md](.agents/rules/html2canvas_pdf_export_rules.md) (sin `truncate`/`overflow:hidden` en texto, imágenes con `max-h-[..] max-w-[..] w-auto h-auto`, A4 de 850×1202 px con cabecera de 76 px y pie de 42 px). Todo texto del documento se declara en `shared/documentTexts/` y se edita en la hoja con `<EditableText k="…">` (ver [docs/PROPOSAL_DOCUMENT_EDITOR.md](docs/PROPOSAL_DOCUMENT_EDITOR.md)); el cromo de edición lleva `data-pdf-chrome` y nunca entra en el PDF; la propuesta web recibe los textos como `doc:<clave>`.
- Producción: no desplegar ni tocar `app-server` sin solicitud explícita; procedimiento en [docs/INFRASTRUCTURE_ARCHITECTURE.md](docs/INFRASTRUCTURE_ARCHITECTURE.md) (acceso por LAN o, desde fuera, por Tailscale con el salto por el nodo Proxmox; direcciones y usuarios en el archivo local no versionado `docs/private/ACCESO_PRODUCCION.md`; checkpoint, ensayo, imagen etiquetada `<versión>-<sha>`, Worker con `wrangler` y rollback).

## Gates antes de dar un trabajo por terminado

Los mismos de `.github/workflows/verify.yml`, que los reparte en trabajos paralelos; el check requerido es `gates` ([CI](docs/QA.md#integración-continua)):

```bash
npm run lint
npm test                      # una suite: npm test -- <filtro>; CI: npm test -- --shard=i/3
npm run build
npm run build:electron
npm --prefix server test
npm --prefix server run format:check
npm --prefix server run build
docker build -f server/Dockerfile -t solarsim-api:qa-modular .
npx tsx server/tests/containerSmoke.ts
npm --prefix workers/share-viewer test
npm --prefix workers/share-viewer run build
npm --prefix mcp-remote test           # incluye la prueba de extremo a extremo con PostgreSQL efímero
npm --prefix mcp-remote run format:check
npm --prefix mcp-remote run build
docker build -f mcp-remote/Dockerfile -t solarsim-mcp-remote:qa .
npx tsx mcp-remote/tests/containerSmoke.ts
```

CI también ejecuta `node scripts/qa/validatePackager.mjs`, `node scripts/qa/devSmoke.mjs`, `node scripts/qa/testPrepareSecrets.mjs` y `npx tsx --test scripts/qa/tests/*.test.ts`; un PR que solo cambia Markdown o `docs/` omite builds y pruebas. Escribir la prueba antes del cambio (en refactors, una prueba de caracterización que fije el comportamiento actual). Si cambia la estructura del repositorio, ejecutar `npm run context:pack`. No afirmar ausencia de vulnerabilidades sin un `npm audit` actual.

## Flujo de trabajo

`beta` es desarrollo; `main` recibe releases estables (merge de `beta` y hotfixes). Conventional Commits (`feat(scope): ...`). Los PR siguen la plantilla de `.github/` y se revisan según [REVIEW.md](REVIEW.md) (revisor automático consultivo con Claude; proceso en [docs/QA.md](docs/QA.md#revisión-de-pr)). Releases: [docs/MAINTENANCE_AND_UPDATES.md](docs/MAINTENANCE_AND_UPDATES.md). Documentación y textos de UI en español; no crear documentos fechados ni bitácoras: la evidencia va en el PR o commit.
